# 第3章 Java 内存模型（JMM）：线程如何看到数据

> 为什么线程 A 写了一个变量，线程 B 却看不到？为什么代码的执行顺序可能和你写的不一样？`volatile` 到底保证了什么？`synchronized` 又保证了什么？Java 内存模型（JMM）是理解一切并发问题的理论基础——它定义了多线程环境下，"写入何时对其他线程可见"的规则。不理解 JMM，你写的每一行并发代码都是在碰运气。

---

## 3.1 为什么需要 JMM

### 3.1.1 矛盾的根源：硬件的"善意欺骗"

在单线程世界里，程序员天然认为：代码从上往下执行，写入的值立刻能读到。但这个"常识"在多核时代被打破了。

**第一个破坏者：CPU 缓存**

现代 CPU 采用多级缓存架构。每个核心都有自己的 L1 和 L2 缓存，多个核心共享 L3 缓存，最后才是主内存（DRAM）。

```text
┌─────────────────────────────────────────────────┐
│                        CPU 芯片                  │
│  ┌─────────────────┐       ┌────────────────┐   │
│  │   Core 0        │       │   Core 1       │   │
│  │  ┌─────────┐    │       │  ┌─────────┐   │   │
│  │  │ L1 Cache│    │       │  │ L1 Cache│   │   │
│  │  │ (私有)   │    │       │  │ (私有)  │   │   │
│  │  └─────────┘    │       │  └─────────┘   │   │
│  │  ┌─────────┐    │       │  ┌─────────┐   │   │
│  │  │ L2 Cache│    │       │  │ L2 Cache│   │   │
│  │  │ (私有)   │    │       │  │ (私有)  │   │   │
│  │  └─────────┘    │       │  └─────────┘   │   │
│  └──────┬──────────┘       └──────┬─────────┘   │
│         │                         │             │
│         └─────────┬───────────────┘             │
│           ┌───────┴───────┐                     │
│           │  L3 Cache     │                     │
│           │  (共享)        │                     │
│           └───────┬───────┘                     │
└───────────────────┼─────────────────────────────┘
            ┌───────┴───────┐
            │  主内存 (DRAM) │
            └───────────────┘
```

当 Core 0 修改变量 `x = 1` 时，这个修改首先写入 Core 0 的 L1 Cache，**不一定立刻写回主内存**。此时 Core 1 读取 `x`，它看到的可能是自己 L1 Cache 中的旧值 `0`。

这就是**可见性问题**的硬件根源。

**第二个破坏者：编译器和 CPU 优化**

为了提升性能，编译器和 CPU 会对指令进行**重排序（Reordering）**：

```java
// 你写的代码
int a = 1;       // ①
int b = 2;       // ②
int c = a + b;   // ③
```

编译器/CPU 可能将执行顺序调整为 ② → ① → ③，因为在单线程语义下，① 和 ② 之间没有依赖关系，调换顺序不影响结果。但在多线程环境下，这种重排序可能产生灾难性后果（经典案例见 3.3.3 节的 DCL 问题）。

### 3.1.2 JMM 的诞生

面对硬件缓存和编译器优化带来的可见性、有序性问题，Java 需要一个**规范**来告诉程序员：

- 什么情况下，一个线程的写入对另一个线程是可见的
- 什么情况下，指令可能被重排序
- 如何通过语言层面的机制（`volatile`、`synchronized`、`final`）来建立必要的保证

这就是 **Java 内存模型（Java Memory Model, JMM）**，定义在 **JSR-133**（Java 5 引入，Java 内存模型与线程规范）中。

## 3.2 JMM 的抽象

### 3.2.1 JMM 不是物理内存模型

首先要澄清一个常见误解：**JMM 描述的不是物理内存的组织方式**（那是硬件的事），而是 **Java 语言对并发内存访问规则的抽象规范**。

JMM 定义的核心问题只有一个：

> **在什么条件下，线程 A 对变量 V 的写入，对线程 B 的后续读取是可见的？**

### 3.2.2 主内存与工作内存

JMM 将内存抽象为两个概念：

| 概念 | 对应现实 | 说明 |
| :-- | :-- | :-- |
| **主内存（Main Memory）** | 堆内存（实例字段、静态字段、数组元素） | 所有线程共享 |
| **工作内存（Working Memory）** | CPU 缓存 + 寄存器 + 编译器优化的暂存 | 每个线程私有 |

```text
┌──────────────┐          ┌──────────────┐
│   线程 A      │          │   线程 B     │
│              │          │              │
│  ┌────────┐  │          │  ┌────────┐  │
│  │工作内存 │   │         │  │工作内存  │  │
│  │ x = ?  │  │          │  │ x = ?  │  │
│  └────┬───┘  │          │  └────┬───┘  │
│       │ load │          │       │ load │
└───────┼──────┘          └───────┼──────┘
        │                         │
        │    ┌───────────────┐    │
        └───►│    主内存      │◄───┘
             │   x = 0       │
             └───────────────┘
```

**关键规则**：

- 线程对变量的所有操作（读/写）都必须在工作内存中进行，**不能直接操作主内存**
- 线程要读取主内存中的变量，必须先将变量从主内存"加载"到工作内存
- 线程要将修改写回主内存，必须先将工作内存中的值"存储"到主内存
- 不同线程之间无法直接访问对方的工作内存，**变量值的传递必须经过主内存**

这个模型解释了为什么线程 A 的写入对线程 B 不可见——修改还停留在 A 的工作内存中，尚未写回主内存，或者 B 的工作内存中还是旧值。

### 3.2.3 JMM 是谁的"契约"

JMM 不仅仅是给程序员看的文档。它是 JVM 实现、JIT 编译器、CPU 都必须遵守的**规范契约**：

- **JIT 编译器**：不能将有 happens-before 关系的操作重排序到违反规则的程度
- **JVM 实现**：必须在适当的位置插入内存屏障指令
- **CPU**：内存屏障指令确保特定的缓存一致性行为

作为 Java 程序员，你需要理解的是这个"契约"中**你该遵守的部分**——即如何正确使用 `volatile`、`synchronized`、`final` 以及 `java.util.concurrent` 包中的工具来保证线程安全。

## 3.3 三大核心问题

JMM 要解决的并发问题可以归结为三类：**原子性**、**可见性**、**有序性**。

### 3.3.1 原子性（Atomicity）

**定义**：一个操作或一系列操作要么全部执行，要么全部不执行，中间不会被其他线程打断。

**经典反例：`i++` 不是原子的**

```java
int i = 0;

// 线程 A 和线程 B 同时执行
i++; // 期望结果是 2，实际可能是 1
```

`i++` 在 JVM 层面分为三步：

```text
1. 读取 i 的当前值    → LOAD i     (从主内存读到工作内存)
2. 将值加 1           → ADD 1       (在工作内存中计算)
3. 将结果写回 i       → STORE i    (从工作内存写回主内存)
```

如果线程 A 在步骤 1 读到 `i = 0`，还未执行步骤 3 时，线程 B 也读到 `i = 0`，最终两个线程都写回 `1`，结果丢失了一次自增。

**JMM 保证的原子性**：

- 对 `long`、`double` 以外的基本类型的读写是原子的（注意：JMM 规范不要求 `long` 和 `double` 的读写是原子的，但现代 JVM 实现通常保证）
- `synchronized` 块内的操作对持有同一锁的线程而言是原子的
- `java.util.concurrent.atomic` 包中的原子类（如 `AtomicInteger`）提供 CAS 级别的原子操作

### 3.3.2 可见性（Visibility）

**定义**：一个线程修改了共享变量的值，其他线程能够立刻看到修改后的值。

**为什么不可见**：如前所述，线程的修改可能停留在工作内存（CPU 缓存）中，尚未写回主内存。其他线程从自己的工作内存中读到的仍是旧值。

```java
// 可见性问题演示
boolean flag = false;
int value = 0;

// 线程 A
value = 42;       // ①
flag = true;      // ②

// 线程 B
while (!flag) {}  // ③ 可能看到 flag 永远是 false
print(value);     // ④ 可能输出 0 而非 42
```

如果没有适当的同步机制，编译器可能将线程 B 中对 `flag` 的读取优化为只读一次（缓存到寄存器），导致 ③ 变成死循环。即使没有这种极端优化，由于 CPU 缓存的存在，④ 处读到的 `value` 也可能不是 `42`。

**JMM 保证可见性的机制**：

| 机制 | 可见性保证 |
| :-- | :-- |
| `volatile` | 写入后立刻刷新到主内存，读取前强制从主内存加载 |
| `synchronized` | 解锁前将工作内存中的值刷新到主内存；加锁后从主内存加载最新值 |
| `final` | 构造函数中对 `final` 字段的写入，在对象引用发布后对所有线程可见 |

### 3.3.3 有序性（Ordering）

**定义**：程序执行的顺序与代码的编写顺序一致。

**为什么无序**：编译器和 CPU 为了优化性能，会对指令进行重排序。在单线程环境下，只要最终结果一致（as-if-serial 语义），重排序是透明的。但在多线程环境下，重排序可能暴露。

**经典案例：DCL（Double-Checked Locking）问题**

```java
// 单例模式的 DCL 实现（在 JDK 5 之前是错误的！）
public class Singleton {
    private static Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {                // ① 第一次检查
            synchronized (Singleton.class) {
                if (instance == null) {        // ② 第二次检查
                    instance = new Singleton(); // ③
                }
            }
        }
        return instance;
    }
}
```

问题出在 ③ 这一行。`new Singleton()` 实际上分为三步：

```text
a. 分配内存空间
b. 执行构造函数，初始化对象
c. 将引用指向分配的内存
```

编译器可能将 b 和 c 重排序为 **c → b**。此时另一个线程在 ① 处看到 `instance != null`，直接返回一个**尚未完成构造的对象**，访问其字段可能得到默认值（`null`、`0` 等）。

**修复方式**：将 `instance` 声明为 `volatile`，禁止重排序：

```java
private static volatile Singleton instance;
```

**JMM 保证有序性的机制**：

| 机制 | 有序性保证 |
| :-- | :-- |
| `volatile` | 禁止其前后的指令被重排序（通过内存屏障实现） |
| `synchronized` | 同一锁保护的代码块内的操作对持有同一锁的线程表现为有序 |

## 3.4 happens-before 规则

### 3.4.1 核心定义

**happens-before**（先行发生）是 JMM 的核心概念，用来判断操作之间的**可见性保证**。

定义（来自 JLS §17.4.5）：

> 如果操作 A happens-before 操作 B，那么 A 的结果对 B 可见（即 B 一定能看到 A 的写入）。并且 A 的执行顺序在 B 之前。

注意：**happens-before 不等于"时间上先执行"**。它是 JMM 定义的一种偏序关系，用于判断可见性，而非实际的执行时序。

### 3.4.2 八条 happens-before 规则

JMM 定义了以下 happens-before 规则（此处列出最重要的六条）：

#### 规则 1：程序顺序规则（Program Order Rule）

**同一线程中**，按照程序代码的顺序，前面的操作 happens-before 后面的操作。

```java
// 线程内
int x = 1;     // A
int y = x + 1; // B
// A hb B（在单线程视角下，B 一定能看到 x = 1）
```

这条规则保证了**单线程内的语义一致性**——你不需要在单线程代码中担心可见性问题。

#### 规则 2：volatile 变量规则（Volatile Variable Rule）

对 `volatile` 变量的**写入** happens-before 后续对该变量的**读取**。

```java
volatile boolean flag = false;
int value = 0;

// 线程 A
value = 42;          // 普通写
flag = true;         // volatile 写  ← A

// 线程 B
while (!flag) {}     // volatile 读  ← B（A hb B）
print(value);        // 一定输出 42
```

由于 A（volatile 写）hb B（volatile 读），根据传递性规则，`value = 42` 对 `print(value)` 也是可见的。

#### 规则 3：锁规则（Monitor Lock Rule）

对一个锁的**解锁**（unlock）happens-before 后续对该锁的**加锁**（lock）。

```java
synchronized (lock) {    // 线程 A 加锁
    sharedVar = 100;     // 修改
}                        // 线程 A 解锁  ← A

synchronized (lock) {    // 线程 B 加锁   ← B（A hb B）
    print(sharedVar);    // 一定输出 100
}
```

#### 规则 4：线程启动规则（Thread Start Rule）

`Thread.start()` happens-before 该线程中的每个操作。

```java
int x = 1;                          // 主线程
Thread t = new Thread(() -> {
    print(x);                       // 一定能看到 x = 1
});
t.start();                          // start() hb print(x)
```

#### 规则 5：线程终止规则（Thread Termination Rule）

线程中的所有操作 happens-before 其他线程检测到该线程已终止（`Thread.join()` 返回，或 `Thread.isAlive()` 返回 `false`）。

```java
int result = 0;

Thread t = new Thread(() -> {
    result = 42;                    // A
});
t.start();
t.join();                           // B（A hb B）
print(result);                      // 一定输出 42
```

#### 规则 6：传递性规则（Transitivity Rule）

如果 A hb B，且 B hb C，那么 A hb C。

这是构建 happens-before 链的关键。正是通过传递性，我们可以跨越多个操作建立可见性保证。

```java
volatile int a = 0;
int b = 0;

// 线程 A
b = 10;         // ①
a = 1;          // ② volatile 写

// 线程 B
while (a != 1); // ③ volatile 读
print(b);       // ④ 一定输出 10

// 推导链：
// ① 程序顺序 hb ② （线程 A 内部）
// ② volatile 写 hb ③ volatile 读 （volatile 规则）
// ③ 程序顺序 hb ④ （线程 B 内部）
// 由传递性：① hb ④ → b = 10 对 ④ 可见
```

### 3.4.3 用 happens-before 分析实际问题

回到前面的 DCL 问题，用 happens-before 来分析：

```java
private static volatile Singleton instance;

// 线程 A：创建实例
instance = new Singleton();
// 等价于：分配内存 → 初始化对象 → 引用赋值
// 由于 instance 是 volatile，volatile 写禁止重排序
// 所以初始化 happens-before 引用赋值

// 线程 B：读取实例
if (instance != null) {
    // volatile 读，与线程 A 的 volatile 写建立 hb 关系
    // 由传递性：对象初始化 hb 这里
    // 所以看到的 instance 一定是完全构造好的
}
```

## 3.5 JMM 与硬件的连接

### 3.5.1 内存屏障

JMM 定义的是 Java 层面的并发语义：哪些写入必须可见，哪些顺序不能被打乱。CPU 和编译器执行的是机器指令，它们负责性能优化，也会引入缓存、写缓冲区和乱序执行。

JVM 需要把 JMM 的语义翻译成具体的执行约束，这个翻译过程主要依赖 **内存屏障（Memory Barrier / Memory Fence）**。

内存屏障的作用可以概括成四点：

- 约束某些读写不能跨越边界重排
- 约束某些写入必须先完成，再执行后续操作
- 让部分写入更快地对其他处理器可见
- 让部分读取从更可靠的位置重新获取数据

如果没有这层约束，happens-before 规则很难真正落到硬件上。语言层面要求"前面的写对后面的读可见"，硬件层面却可能因为缓存和乱序执行，让另一个核心暂时看不到这个结果。

### 3.5.2 四种内存屏障

JMM 讨论底层实现时，通常用四类屏障描述重排序边界：

| 屏障类型 | 作用 | 对应的 JMM 场景 |
| :-- | :-- | :-- |
| **LoadLoad** | 屏障前的读操作完成后，才能执行屏障后的读操作 | 确保读取顺序 |
| **StoreStore** | 屏障前的写操作完成后，才能执行屏障后的写操作 | `volatile` 写之前 |
| **LoadStore** | 屏障前的读操作完成后，才能执行屏障后的写操作 | 较少使用 |
| **StoreLoad** | 屏障前的写操作完成后，才能执行屏障后的读操作 | `volatile` 写之后（最昂贵的屏障） |

其中开销最大的一般是 **StoreLoad**。它既要处理写入的可见性，又要阻止后续读取穿越过来，因此在很多处理器架构上都更昂贵。

### 3.5.3 屏障约束的是什么

```text
线程中的操作流

读 A ── 读 B ── 写 C ── 写 D
          ↑
       插入屏障后
          ↓

读 A ── [Barrier] ── 读 B ── 写 C ── 写 D
```

屏障本身不承担业务逻辑，它做的是**约束边界**：告诉编译器和 CPU，某些读写不能跨过这条线乱跑。

这层约束带来的结果是：

- 前面的操作必须按要求先完成
- 后面的操作必须按要求后执行
- 某些写入会按照同步语义对外可见
- 某些读取会在正确的同步点之后发生

### 3.5.4 不同 CPU 架构

不同 CPU 架构对内存一致性的默认保证并不一样，这也是 JMM 必须存在的原因。

| CPU 架构 | 内存模型强度 | 特点 |
| :-- | :-- | :-- |
| **x86 / x86-64** | 较强（TSO） | 硬件默认已经处理了一部分顺序问题，但不是全部 |
| **ARM / AArch64** | 较弱 | 更依赖显式屏障，JVM 需要更明确地表达顺序要求 |
| **RISC-V** | 较弱（可配置） | 通过显式 `fence` 指令控制约束 |

这也是并发 bug 容易出现平台差异的原因：同一段代码在 x86 上看起来比较稳定，迁移到 ARM 后却可能立刻暴露问题。真正稳定、可推理的保证，来自 JMM 语义和 JVM 插入的同步约束，而不是某一种硬件恰好替你兜底。

### 3.5.5 JMM、JVM 与 CPU

JMM、JVM 与 CPU 的关系可以概括成三层：

```text
┌──────────────────────────────┐
│ Java 语言层：happens-before  │
│ volatile / synchronized 等   │
└──────────────┬───────────────┘
               │ 语义落实
┌──────────────▼───────────────┐
│ JVM / JIT：插入合适的屏障与约束 │
└──────────────┬───────────────┘
               │ 指令执行
┌──────────────▼───────────────┐
│ CPU：缓存、一致性协议、乱序执行 │
└──────────────────────────────┘
```

JMM 负责定义并发语义，JVM 负责把语义翻译成具体的屏障与顺序约束，CPU 负责执行这些约束。

在 Java 并发工具中：

- `volatile` 通过变量级别的同步约束建立可见性与有序性，见第 4 章
- `synchronized` 通过加锁与解锁建立临界区的互斥、可见性与有序性，见第 5 章

## 3.6 本章小结

Java 并发中的核心内存语义，可以归纳为：

| 问题 | 根源 | 解决方案 |
| :-- | :-- | :-- |
| **原子性** | 操作被中间打断 | `synchronized`、`AtomicXxx`、CAS |
| **可见性** | CPU 缓存 + 编译器优化 | `volatile`、`synchronized`、`final` |
| **有序性** | 指令重排序 | `volatile`（内存屏障）、`synchronized` |

**happens-before 规则**是 JMM 的核心判断工具：如果两个操作之间存在 happens-before 关系，那么前一个操作的结果对后一个操作可见。通过程序顺序规则、volatile 规则、锁规则、线程启动/终止规则和传递性，我们可以推理出复杂的可见性保证。

**内存屏障**是 JMM 在硬件层面的实现手段，JVM 在 `volatile` 读写和 `synchronized` 操作的前后插入适当的屏障指令，确保 JMM 语义在不同 CPU 架构上得到正确实现。

有了这些规则，`volatile`（第 4 章）、`synchronized`（第 5 章）、`ReentrantLock`（第 6 章）、`ConcurrentHashMap`（第 8 章）等工具的行为就能继续被推理出来。你不必停留在"记住用法"，而是可以判断它为什么需要、它保证了什么、它不保证什么。
