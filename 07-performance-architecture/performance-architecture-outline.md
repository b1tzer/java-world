# 第七卷 性能与架构 —— 系统如何在高并发、大规模场景下持续演进

> 如果前六卷是在培养一个能够写出高质量 Java 后端服务的工程师，那么第七卷培养的是一个能够**设计复杂业务系统**的工程师。前六卷解决的是局部能力（会写 Java → 懂 JVM → 懂并发 → 懂网络 → 懂数据 → 懂企业框架），第七卷需要把这些能力**组合起来**，回答：系统为什么这样拆？如何保证高可用？如何支撑百万用户？如何权衡性能与一致性？本卷从架构本质出发，逐步覆盖分层设计与 DDD、高并发与高可用、分布式一致性、大规模数据系统、消息驱动架构、API 治理、云原生、性能工程，最终通过三个综合案例完成全书闭环。

## 1 软件系统架构思想：从代码到系统

本章目标：建立架构思维。区分"代码设计"与"架构设计"，理解架构的本质不是在真空中选技术，而是在约束条件下寻找合理的系统结构。

### 1.1 什么是软件架构

区分两个层次：

| 代码设计 | 架构设计 |
|---------|---------|
| `class` / `method` / `module` | `service` / `database` / `network` / `deployment` |
| 关注：代码怎么组织 | 关注：系统怎么拆分与协作 |

架构是把功能需求翻译成系统结构的桥梁。

### 1.2 为什么需要架构

小型系统不需要复杂的架构思考——一个应用 + 一个数据库足够。

大型系统需要架构来解决：

| 维度 | 问题 |
|------|------|
| 性能 | 用户量上去，单机扛不住 |
| 可维护性 | 代码量膨胀，改一处牵动全身 |
| 扩展性 | 新需求加入，系统能不能"加模块"而非"重写" |
| 稳定性 | 单点故障不能导致全站崩溃 |

### 1.3 架构设计的本质

**不是技术选型**，而是在约束条件下寻找合理的系统结构。

约束三角：用户规模 ⇄ 成本 ⇄ 业务复杂度 ⇄ 团队能力

好的架构是用当前成本解决当前问题，同时为未来保留扩展空间。过度设计（微服务地狱）和不足设计（单体泥球）都是陷阱。

### 1.4 架构演进规律

理解演进线路比死记架构名称更重要：

```
单体 → 垂直拆分 → SOA → 微服务 → 云原生
```

演进的驱动力：用户规模增长 → 流量压力 → 组织膨胀（多个团队）→ 需要更细粒度的分治。

## 2 分层架构与模块设计

本章目标：理解分层的本质是管理复杂度。不管是经典 MVC、六边形架构还是 Clean Architecture，核心思想都是"让核心业务逻辑不依赖外部细节"。

### 2.1 为什么需要分层

分层的核心收益：**控制依赖方向**。

经典三层：

```
Controller（接收请求、参数校验）
      ↓
Service（业务逻辑编排）
      ↓
Repository（数据访问）
      ↓
Database
```

每一层只依赖下一层，不反向依赖，这样替换下层不影响上层。

### 2.2 六边形架构（Ports & Adapters）

核心思想：**业务核心不依赖外部**。

```
外部世界（HTTP / MQ / DB / File）
      ↕ 通过 Adapter 连接
Port（抽象接口）
      ↕
Domain Core（纯业务逻辑）
```

端口定义契约，适配器实现契约。更换数据库只需换 Adapter，业务核心不动。

### 2.3 Clean Architecture

与六边形架构一脉相承，强调**依赖方向只从外向内**：

```
Frameworks & Drivers
      ↓
Interface Adapters
      ↓
Application Business Rules
      ↓
Enterprise Business Rules（最内层，最抽象）
```

外层变化不影响内层。

### 2.4 模块边界设计

| 原则 | 含义 | 反面 |
|------|------|------|
| 高内聚 | 一起变的东西放在一起 | 改一个功能要改 N 个包 |
| 低耦合 | 模块间通过接口交互 | A 模块直接操作 B 模块的数据库 |
| 单一职责 | 一个模块只有一个要改的原因 | 用户模块里写了订单逻辑 |

## 3 领域驱动设计（DDD）

本章目标：DDD 是中高级 Java 开发者的重要分水岭。理解传统 CRUD 方式在复杂系统中为什么失效，以及如何用领域模型驱动代码设计。

### 3.1 为什么传统 CRUD 会失效

| 系统类型 | 数据特征 | 设计方式 |
|---------|---------|---------|
| 简单系统 | 表驱动，一个表一个 CRUD | 数据库先行，代码是表结构的映射 |
| 复杂系统 | 业务规则驱动，一次操作涉及多处校验和状态变更 | 需先理解业务，再建模 |

当业务规则散落在 Service 层的 `if/else` 中，系统越来越难改——DDD 的价值在于用模型承载规则。

### 3.2 DDD 核心概念

| 概念 | 含义 | 举例 |
|------|------|------|
| Entity | 有唯一标识，可变 | Order（订单 ID 不变，状态可流转） |
| Value Object | 无标识，不可变 | Money（金额 + 币种，值相同即可互换） |
| Aggregate | 一组相关对象的聚合根 | Order（聚合根）+ OrderItem（内部实体） |
| Aggregate Root | 聚合的入口，保证内部一致性 | 对 OrderItem 的操作必须通过 Order |

### 3.3 领域建模过程

```
业务分析（和领域专家沟通）
      ↓
识别核心概念 → Entity / Value Object / Aggregate
      ↓
划分 Bounded Context
      ↓
代码模型落地
```

关键：模型必须反映业务语言，不是数据库表的镜像。

### 3.4 战略设计

- **Bounded Context（限界上下文）**：每个上下文有自己的模型语言，同一事物在不同上下文中可能有不同含义（如"用户"在订单上下文和营销上下文中关注不同属性）
- **Context Map**：上下文之间的映射关系（上游/下游、防腐层、共享内核）

### 3.5 战术设计

落地的具体模式：Entity、Value Object、Repository（仓储接口，定义在领域层）、Domain Service（无状态、跨实体的领域逻辑）、Application Service（编排用例流程）。

核心原则：**领域层不依赖任何框架**——没有 `@Autowired`，没有 `@Entity`。

## 4 高并发系统设计

本章目标：连接第三卷并发与第五卷数据访问——理解高并发的本质是资源竞争，以及从架构层面如何应对。

### 4.1 高并发问题本质

核心：**资源竞争**。

| 竞争资源 | 典型瓶颈 |
|---------|---------|
| CPU | 计算密集型任务耗尽核心 |
| 内存 | 大量并发对象 → GC 停顿 |
| I/O | 网络带宽、磁盘吞吐 |
| 数据库 | 连接数、锁竞争 |

### 4.2 流量模型分析

关键指标：

| 指标 | 含义 |
|------|------|
| QPS（Query Per Second） | 每秒请求数 |
| TPS（Transaction Per Second） | 每秒事务数 |
| RT（Response Time） | 响应时间，关注 P50 / P99 |
| 并发数 | 同一时刻处理的请求数 |

经验公式：`并发数 = QPS × 平均 RT`。

### 4.3 水平扩展

从单机性能优化到增加机器：

- **垂直扩展**：加 CPU、加内存，有上限
- **水平扩展**：加机器，理论上无限，前提是服务无状态

### 4.4 无状态服务设计

为什么决定服务能否随意扩容：

- **有状态**：请求必须路由到某台机器（Session 粘滞）→ 无法随意扩容
- **无状态**：任意机器都能处理任意请求 → 可随意加减机器

实践：Session 外置到 Redis，Cookie 携带 Token。

### 4.5 高并发经典架构

```
用户请求 → CDN（静态资源）
              ↓
         API Gateway（鉴权、限流、路由）
              ↓
         Service（无状态，可水平扩展）
              ↓
         Cache（Redis，热点数据）
              ↓
         Database（主从 + 分库分表）
```

逐层消峰，逐层缓存，逐层降级。

## 5 高可用系统设计

本章目标：理解"可用性"是一个可量化的工程指标（99.9% vs 99.99%），以及保证高可用的核心手段：冗余、隔离、降级。

### 5.1 可用性的量化

| 级别 | 年不可用时间 | 允许的运维模式 |
|------|------------|---------------|
| 99.9%（三个九） | 约 8.76 小时 | 允许有计划的夜间停机 |
| 99.99%（四个九） | 约 52 分钟 | 不允许计划内停机 |
| 99.999%（五个九） | 约 5 分钟 | 极高投入，核心支付系统级别 |

### 5.2 单点故障（SPOF）

任何一台机器/一个服务/一个网络节点挂掉就会影响全局，就是单点。高可用的第一步：**消除所有单点**。

### 5.3 冗余设计

| 模式 | 方式 | 适用场景 |
|------|------|---------|
| 主备（Active-Standby） | 主节点工作，备节点待命 | 数据库 |
| 集群（Active-Active） | 多节点同时工作 | 无状态服务 |
| 多副本 | 数据存多份 | 存储层 |

### 5.4 故障隔离

让故障只影响局部，不影响全局：

| 策略 | 含义 |
|------|------|
| 服务隔离 | 一个服务挂不影响其他服务 |
| 线程池隔离 | 为不同接口分配独立线程池 |
| 舱壁模式（Bulkhead） | 限制单个下游的并发连接数 |

### 5.5 优雅降级

不是"挂了就不提供服务"，而是"挂了还能提供部分服务"：

| 策略 | 行为 |
|------|------|
| Fallback | 调用失败返回默认值或缓存数据 |
| 熔断 | 错误率超过阈值时快速失败，不再调用故障服务 |
| 降级 | 高峰时关闭非核心功能，保证核心链路 |

## 6 分布式系统核心问题

本章目标：分布式系统的复杂性来自"网络不可靠"这一根本事实。理解 CAP 不是一道选择题，而是一个约束——分区发生时，你必须在一致性与可用性之间做取舍。

### 6.1 分布式系统为什么复杂

根本原因：网络不可靠。
- 延迟不确定
- 数据包可能丢失
- 节点随时可能故障

在单机上认为理所当然的事（如 `if (x == 1)` 立刻得到结果），在分布式系统中需要额外的共识协议。

### 6.2 CAP 理论

由 Eric Brewer 提出：

| 字母 | 含义 |
|------|------|
| C（Consistency） | 所有节点在同一时刻看到相同数据 |
| A（Availability） | 每个请求都能得到非错误的响应 |
| P（Partition Tolerance） | 系统在部分节点无法通信时仍能工作 |

关键理解：P 是必须面对的（网络分区无法避免），CAP 的本质是 **分区发生时，选 C 还是选 A**。

### 6.3 一致性模型

| 级别 | 行为 | 示例 |
|------|------|------|
| 强一致 | 写入后立刻对所有后续读可见 | 关系数据库主库 |
| 弱一致 | 不保证立即可见 | DNS |
| 最终一致 | 经过一段时间后最终一致 | DNS、DNS 多数分布式系统 |

### 6.4 分布式事务

| 方案 | 原理 | 适用场景 |
|------|------|---------|
| 2PC（两阶段提交） | 协调者先问所有参与者是否就绪，再统一提交 | 强一致要求，但性能差 |
| TCC（Try-Confirm-Cancel） | 预留资源 → 确认 → 取消，业务层面两阶段 | 资金交易类场景 |
| Saga | 长事务拆分为多个本地事务 + 补偿操作 | 微服务间的数据一致性 |

### 6.5 分布式锁

| 方案 | 特点 |
|------|------|
| Redis（SET NX + 过期时间） | 高性能，但有锁过期风险，Redisson 提供看门狗 |
| ZooKeeper（临时顺序节点） | 可靠性高，连接断开自动释放，但性能低于 Redis |
| 数据库（唯一索引 + 乐观锁） | 最简单，但性能最差 |

## 7 大规模数据系统设计

本章目标：连接第五卷——从百万级到十亿级数据，回答"数据涨了怎么办"。核心手段：分库分表、冷热分离、搜索系统、数据一致性保障。

### 7.1 数据增长的必然性

```
单表百万行：索引有效，查询正常
单表千万行：索引开始吃力，JOIN 性能下降
单表上亿行：不拆分无法继续
```

### 7.2 分库分表设计

三个核心问题：

| 问题 | 决策 |
|------|------|
| 分片键选什么？ | 选最常用的查询条件（通常 user_id 或 order_id） |
| 如何路由？ | 中间件（ShardingSphere）或客户端路由 |
| 如何扩容？ | 停机扩容 vs 平滑扩容（一致性哈希 + 数据迁移） |

分片键选错是灾难——跨片查询、跨片排序、跨片事务都会大幅增加复杂度。

### 7.3 海量数据检索

MySQL 不适合全文搜索 → Elasticsearch：

倒排索引把词映射到文档，搜索速度与数据量关系不大，适合日志检索、商品搜索等场景。

### 7.4 数据冷热分离

| 数据类型 | 占比 | 存储 | 访问频率 |
|---------|------|------|---------|
| 热数据 | ~10% | 高性能存储（内存/SSD） | 高频 |
| 温数据 | ~30% | 普通数据库 | 中频 |
| 冷数据 | ~60% | 低成本存储（归档） | 低频 |

### 7.5 数据一致性策略

当数据在多个地方（MySQL + Redis + ES），如何保持一致：

| 策略 | 方式 | 风险 |
|------|------|------|
| 双写 | 同时写 MySQL 和 Redis | 部分失败导致不一致 |
| 异步同步 | Canal 监听 binlog → 同步到 ES/Redis | 有延迟 |
| 最终一致 + 对账 | 异步同步 + 定时任务校验修复 | 需接受短时间不一致 |

## 8 消息驱动架构

本章目标：理解异步不是"让请求变快"的银弹，而是解耦生产者和消费者的架构手段。

### 8.1 为什么需要异步

同步链路的局限：

```
Request → Service A → Service B → Service C → Response
```

链路过长，任意环节阻塞都会拖慢整体。异步化后：

```
Request → Service A → MQ → Service B（异步消费）→ Service C（异步消费）
```

### 8.2 事件驱动设计

核心是 Event（事件）：**"什么事发生了"**。生产者发布事件，消费者订阅事件，双方通过 MQ 解耦，互不知道对方存在。

### 8.3 Kafka 在大型系统中的角色

| 场景 | 用法 |
|------|------|
| 日志采集 | 各服务日志 → Kafka → ELK |
| 数据同步 | binlog → Kafka → 下游 |
| 异步解耦 | 下单事件 → Kafka → 库存/通知/积分多个消费者 |
| 流计算 | Kafka → Flink → 实时报表 |

### 8.4 消息可靠性

| 机制 | 作用 |
|------|------|
| 消息持久化 | 落盘，重启不丢 |
| 消费者 ACK | 处理完再确认，失败不确认则重推 |
| 幂等消费 | 相同消息重复消费结果不变（数据库唯一约束 + 业务幂等） |
| 死信队列 | 多次重试失败的消息路由到死信队列，人工介入 |

## 9 API 治理与服务设计

本章目标：API 是系统对外的契约。理解 REST 不是"URL 风格"，而是对资源的一套操作语义；理解服务治理（限流、熔断、灰度发布）是保障 API 稳定性的必选项。

### 9.1 API 设计原则

REST 的核心不是 URL 格式，而是**面向资源**：

| 操作 | HTTP 方法 | URL | 含义 |
|------|----------|-----|------|
| 查询用户列表 | GET | `/users` | 获取资源集合 |
| 查询某个用户 | GET | `/users/{id}` | 获取单个资源 |
| 创建用户 | POST | `/users` | 创建资源 |
| 更新用户 | PUT | `/users/{id}` | 全量更新资源 |
| 删除用户 | DELETE | `/users/{id}` | 删除资源 |

**版本管理**：URL 前缀（`/v1/`, `/v2/`）或 Header，保证向后兼容。

### 9.2 服务注册发现

```
Provider 启动 → 向 Registry 注册
Consumer 启动 → 向 Registry 订阅 → 获取 Provider 地址列表
Consumer 调用 Provider → 负载均衡选择节点
```

### 9.3 服务治理

| 能力 | 含义 | 工具 |
|------|------|------|
| 限流 | 控制单位时间请求量 | Sentinel、令牌桶/漏桶算法 |
| 熔断 | 错误率高时快速失败 | Hystrix → Resilience4j |
| 重试 | 失败后自动重试 | 需保证幂等 |
| 降级 | 返回兜底逻辑 | 高峰期/故障时启用 |

### 9.4 灰度发布

| 方式 | 原理 |
|------|------|
| 金丝雀发布 | 先放 1%~5% 流量到新版本，观测无问题后全量 |
| 蓝绿部署 | 新老版本两套环境并存，切换流量 |
| 流量切分 | 按用户 ID、地区、Header 等路由到不同版本 |

## 10 云原生架构

本章目标：云原生不是"用 Docker 部署"，而是让应用充分利用云平台的弹性、自动化和标准化能力。

### 10.1 从物理机到云

```
物理机时代：买机器、装系统、配网络，周期以周计
虚拟化时代：VM 分钟级交付
容器化时代：容器秒级启动
Serverless：函数即服务，自动伸缩
```

### 10.2 Docker 容器化

核心概念：Image（构建产物）+ Container（运行实例）。一切依赖打包进镜像，环境一致，随处运行。

### 10.3 Kubernetes 编排

| 概念 | 职责 |
|------|------|
| Pod | 最小调度单元，一个或多个容器共享网络和存储 |
| Deployment | 声明副本数、滚动更新策略 |
| Service | 为 Pod 提供稳定的访问入口（ClusterIP / NodePort / LoadBalancer） |
| ConfigMap / Secret | 配置与代码分离 |

### 10.4 Service Mesh

将服务间的通信控制下沉到 Sidecar 代理层，服务本身无需关心重试、熔断、流量路由，由 Mesh 统一处理。代表：Istio。

## 11 系统性能工程

本章目标：性能优化不是凭感觉调参数，而是一套科学的闭环流程。连接第二卷 JVM 知识——GC、内存、线程分析工具在线上性能诊断中的实战应用。

### 11.1 性能指标体系

| 指标 | 含义 | 关注点 |
|------|------|--------|
| Latency（延迟） | 单个请求的处理时间 | P50 / P95 / P99 |
| Throughput（吞吐） | 单位时间处理的请求量 | 系统瓶颈在哪里 |
| Error Rate | 错误请求占比 | 异常增长需立即响应 |
| Saturation | 资源饱和度 | CPU / 内存 / I/O / 连接数 |

### 11.2 性能分析方法

| 方法 | 工具 | 场景 |
|------|------|------|
| Profiling | Arthas、JProfiler、async-profiler | 定位 CPU 热点、内存分配 |
| Benchmark | JMH | 微基准测试，评估代码片段性能 |
| 压测 | JMeter、wrk | 评估系统在给定负载下的表现 |

### 11.3 JVM 与系统性能的连接

连接第二卷知识，线上实战场景：

| 场景 | JVM 工具 |
|------|---------|
| CPU 100% | Arthas `thread -n 3` 找前三个忙线程 + `jstack` 看栈 |
| 内存泄漏 | `jmap -histo` 看对象分布 + MAT 分析 heap dump |
| 频繁 GC | `jstat -gcutil` 观察 GC 次数和耗时 |
| 接口变慢 | 结合 Tracing 定位慢调用链 |

### 11.4 性能优化方法论

```
发现问题（监控 / 压测）
      ↓
定位瓶颈（Profiling / Tracing / 日志）
      ↓
提出假设 → 改动 → 验证
      ↓
持续监控，防止回退
```

核心原则：**不要盲目优化**——没有测量就没有优化。先确认瓶颈在哪，再对症下药。

## 12 架构案例分析

本章目标：综合全书能力，通过三个接近真实业务的案例，学习如何在具体约束下做架构设计决策。

### 12.1 案例一：高并发秒杀系统

涉及知识点：第三卷（并发安全）、第五卷（缓存、数据库）、第七卷（限流、削峰、异步）。

关键设计：

| 问题 | 方案 |
|------|------|
| 瞬时高流量 | 网关限流 + CDN 静态化 + 验证码削峰 |
| 库存扣减超卖 | Redis 预减库存 + Lua 原子操作 |
| 订单异步处理 | 扣减成功 → 发 MQ → 订单服务异步生成订单 |
| 保证下单成功 | 分布式事务（本地事务表 + 消息重试） |

### 12.2 案例二：社交 Feed 流系统

涉及知识点：第四卷（网络通信）、第五卷（缓存、数据库）、第七卷（推送 vs 拉取、冷热分离）。

| 问题 | 方案 |
|------|------|
| Feed 推还是拉 | 大 V 用"拉"（粉丝拉取），普通用户用"推"（写入时扩散） |
| 热点缓存 | 热门 Feed 缓存到 Redis，不穿透到 DB |
| 时间线一致性 | 版本号 + 增量同步 |
| 海量数据存储 | 按 user_id 分片 + 冷热分离 |

### 12.3 案例三：支付系统

涉及知识点：第五卷（事务）、第六卷（安全）、第七卷（一致性、分布式事务）。

| 问题 | 方案 |
|------|------|
| 资金一致性 | TCC 两阶段（Try 冻结 → Confirm 扣款 → Cancel 解冻） |
| 幂等扣款 | 全局唯一交易号 + 数据库唯一约束 |
| 对账 | 定时比对内部流水与第三方账单 |
| 安全 | 鉴权 + 签名验证 + 敏感信息加密 + 操作审计 |
