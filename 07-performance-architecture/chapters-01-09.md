# 第一章 架构思想与分层设计

> 建立架构思维，区分"代码设计"与"架构设计"。

---

## 1.1 什么是软件架构

| 代码设计 | 架构设计 |
|---------|---------|
| class / method / module | service / database / network / deployment |
| 关注代码怎么组织 | 关注系统怎么拆分与协作 |

架构不是技术选型，而是在约束（用户规模、成本、团队、业务复杂度）下寻找合理的系统结构。

## 1.2 架构演进规律

```
单体 → 垂直拆分 → SOA → 微服务 → 云原生
```

演进驱动力：用户规模增长 → 流量压力 → 组织膨胀 → 需要更细粒度的分治。

过度设计（微服务地狱）和不足设计（单体泥球）都是陷阱。好的架构是用当前成本解决当前问题，同时为未来保留扩展空间。

## 1.3 分层架构

```
Controller（接收请求、参数校验）
      ↓
Service（业务逻辑编排）
      ↓
Repository（数据访问）
```

每层只依赖下一层，不反向依赖。替换下层不影响上层。

## 1.4 六边形架构

核心思想：**业务核心不依赖外部**。

```
外部世界（HTTP / MQ / DB）
      ↕ Adapter
Port（抽象接口）
      ↕
Domain Core（纯业务逻辑）
```

更换数据库只需换 Adapter，业务核心不动。

## 1.5 Clean Architecture

依赖方向只从外向内：Frameworks → Adapters → Application Rules → Enterprise Rules。外层变化不影响内层。

## 1.6 模块边界

高内聚（一起变的东西放一起）、低耦合（模块间通过接口交互）、单一职责（一个模块只有一个要改的原因）。

# 第二章 领域驱动设计（DDD）

> 传统 CRUD 在复杂系统中为什么失效，以及如何用领域模型驱动代码设计。

---

## 2.1 为什么传统 CRUD 会失效

简单系统：表驱动，一个表一个 CRUD。复杂系统：业务规则散落在 Service 层的 if/else 中，越来越难改。

DDD 的价值：用模型承载规则。

## 2.2 核心概念

| 概念 | 含义 | 举例 |
|------|------|------|
| Entity | 有唯一标识，可变 | Order（ID 不变，状态可流转） |
| Value Object | 无标识，不可变 | Money（金额 + 币种） |
| Aggregate | 一组相关对象的聚合根 | Order + OrderItem |
| Bounded Context | 上下文有自己的模型语言 | "用户"在订单和营销中含义不同 |

## 2.3 领域建模过程

```
业务分析 → 识别 Entity / Value Object / Aggregate → 划分 Bounded Context → 代码落地
```

模型必须反映业务语言，不是数据库表的镜像。

## 2.4 战术设计

- **Repository**：仓储接口，定义在领域层，不依赖具体 ORM
- **Domain Service**：无状态、跨实体的领域逻辑
- **Application Service**：编排用例流程

核心原则：领域层不依赖任何框架——没有 `@Autowired`，没有 `@Entity`。

# 第三章 高并发系统设计

> 高并发的本质是资源竞争，以及从架构层面如何应对。

---

## 3.1 流量模型

| 指标 | 含义 |
|------|------|
| QPS | 每秒请求数 |
| TPS | 每秒事务数 |
| RT | 响应时间（P50 / P99） |

经验公式：`并发数 = QPS × 平均 RT`。

## 3.2 水平扩展与无状态

- 垂直扩展：加 CPU/内存，有上限
- 水平扩展：加机器，前提是服务无状态

无状态 = 任意机器处理任意请求。实践：Session 外置到 Redis。

## 3.3 高并发经典架构

```
用户请求 → CDN → API Gateway（限流、鉴权）→ Service → Cache → Database
```

逐层消峰，逐层缓存，逐层降级。

# 第四章 高可用系统设计

---

## 4.1 可用性量化

| 级别 | 年不可用时间 |
|------|------------|
| 99.9% | 约 8.76 小时 |
| 99.99% | 约 52 分钟 |
| 99.999% | 约 5 分钟 |

## 4.2 核心手段

消除单点故障、冗余设计（主备/集群/多副本）、故障隔离（服务隔离/线程池隔离/舱壁模式）、优雅降级（Fallback/熔断/降级）。

# 第五章 分布式系统核心问题

---

## 5.1 CAP 理论

P（分区容忍）必须面对。分区发生时：选 C（一致性）还是 A（可用性）。

## 5.2 分布式事务

| 方案 | 原理 | 场景 |
|------|------|------|
| 2PC | 协调者先问再统一提交 | 强一致，性能差 |
| TCC | 预留→确认→取消 | 资金交易 |
| Saga | 本地事务 + 补偿 | 微服务间 |

## 5.3 分布式锁

Redis（SET NX + 过期，Redisson 看门狗）、ZooKeeper（临时顺序节点）、数据库（唯一索引）。

# 第六章 数据架构：缓存与大规模数据

> 合并 Redis 缓存体系和分库分表设计。

---

## 6.1 Java 缓存体系

Jedis → Lettuce（Spring Boot 默认）→ Redisson（高级抽象）。Spring Cache：`@Cacheable` / `@CacheEvict`。

## 6.2 缓存一致性

Cache Aside（更新 DB → 删缓存）、延迟双删。

## 6.3 三大经典问题

| 问题 | 解决 |
|------|------|
| 穿透 | 布隆过滤器 / 缓存空值 |
| 击穿 | 互斥锁 / 逻辑过期 |
| 雪崩 | 过期时间加随机值 |

## 6.4 分库分表

分片键（最常用的查询条件）、路由（ShardingSphere）、扩容（一致性哈希 + 数据迁移）。

## 6.5 数据冷热分离

热数据（~10%，高性能存储）、温数据（~30%，普通库）、冷数据（~60%，归档）。

## 6.6 多数据源一致性

双写（风险高）、Canal 监听 binlog 异步同步、最终一致 + 定时对账。

# 第七章 消息驱动架构

---

## 7.1 同步 vs 异步

同步：请求 → A → B → C → 响应（链路长，阻塞）。异步：请求 → A → MQ → B/C（解耦）。

## 7.2 Kafka 的角色

日志采集、数据同步（binlog → Kafka → 下游）、异步解耦、流计算。

## 7.3 消息可靠性

持久化、消费者 ACK、幂等消费（唯一约束 + 业务幂等）、死信队列。

# 第八章 性能工程

---

## 8.1 性能指标

Latency（P50/P95/P99）、Throughput、Error Rate、Saturation。

## 8.2 分析方法

Profiling（Arthas/JProfiler）、Benchmark（JMH）、压测（JMeter/wrk）。

## 8.3 JVM 性能诊断

| 场景 | 工具 |
|------|------|
| CPU 100% | Arthas `thread -n 3` + jstack |
| 内存泄漏 | jmap + MAT |
| 频繁 GC | jstat -gcutil |

## 8.4 优化方法论

```
发现问题（监控/压测）→ 定位瓶颈 → 假设 → 改动 → 验证 → 持续监控
```

没有测量就没有优化。

# 第九章 架构案例分析

---

## 9.1 高并发秒杀系统

| 问题 | 方案 |
|------|------|
| 瞬时高流量 | 网关限流 + CDN 静态化 + 验证码削峰 |
| 库存超卖 | Redis 预减库存 + Lua 原子操作 |
| 订单异步 | MQ → 订单服务异步生成 |
| 一致性 | 本地事务表 + 消息重试 |

## 9.2 社交 Feed 流

| 问题 | 方案 |
|------|------|
| 推还是拉 | 大 V 拉取，普通用户推送 |
| 热点缓存 | Redis |
| 海量存储 | 按 user_id 分片 + 冷热分离 |

## 9.3 支付系统

| 问题 | 方案 |
|------|------|
| 资金一致性 | TCC（Try 冻结 → Confirm 扣款 → Cancel 解冻） |
| 幂等扣款 | 全局唯一交易号 + 数据库唯一约束 |
| 对账 | 定时比对内部流水与第三方账单 |
| 安全 | 鉴权 + 签名 + 加密 + 审计 |
