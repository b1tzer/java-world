# 第五章 JIT 编译

> 本章回答"为什么 Java 不是一直解释执行，而是越来越快"。精简分层编译细节，聚焦核心机制。

---

## 5.1 为什么需要 JIT

| 模式 | 启动速度 | 峰值性能 | 适用场景 |
|------|---------|---------|---------|
| 解释执行 | 快 | 差 | 小程序、脚本 |
| AOT（提前编译） | 快 | 一般 | 启动敏感场景 |
| JIT（即时编译） | 慢（需要预热） | 最优 | 长期运行的服务端 |

Java 的答案是**混合模式**：先用解释器快速启动，热点代码交给 JIT 编译优化。

这就是为什么 Java 服务启动后需要"预热"——刚开始是解释执行，性能较差；运行一段时间后，热点代码被 JIT 编译成机器码，性能大幅提升。

---

## 5.2 HotSpot 编译体系

```
解释执行（Interpreter）
      ↓ 热点探测（方法调用次数 > 阈值）
C1 编译（Client Compiler）—— 快速编译，保守优化
      ↓ 更热（调用次数进一步增加）
C2 编译（Server Compiler）—— 深度编译，激进优化
```

**分层编译（Tiered Compilation，JDK 8+ 默认）：**

| 阶段 | 编译方式 | 特点 |
|------|---------|------|
| Level 0 | 解释执行 | 启动阶段 |
| Level 1-3 | C1 + 逐步增加 profiling | 收集运行时信息 |
| Level 4 | C2 | 基于 profiling 数据深度优化 |

profiling 收集的信息包括：哪些分支最常走、哪些类型最常出现、哪些方法被频繁调用。C2 利用这些信息做激进优化。

## 5.3 方法内联

**最重要的 JIT 优化，没有之一。**

方法内联将被调用方法的代码直接嵌入调用方，消除方法调用开销（栈帧创建与销毁、参数传递、返回值处理）：

```java
// 内联前
public int add(int a, int b) { return a + b; }
public int calculate() { return add(1, 2) + add(3, 4); }

// 内联后（JIT 优化）
public int calculate() { return 1 + 2 + 3 + 4; }
```

内联不仅消除了方法调用开销，还为后续优化打开了空间——常量折叠（`1 + 2 + 3 + 4 = 10`）、逃逸分析（对象可以栈上分配）都需要在内联之后才能进行。

`-XX:MaxInlineSize` 控制内联阈值（默认 35 字节），小于此大小的方法会被自动内联。

## 5.4 逃逸分析与相关优化

第三章对象模型已经介绍了逃逸分析的概念。JIT 编译器利用逃逸分析的结果做三种优化：

**1. 栈上分配。** 未逃逸的对象在栈帧上创建，方法结束时自动销毁，不需要 GC 回收。这对大量短生命周期对象的场景（如 `new Point(x, y)`）特别有效。

**2. 标量替换。** 将对象拆散为基本类型标量，完全消除对象分配：

```java
// 原始
Point p = new Point(1, 2);
int sum = p.x + p.y;

// 标量替换后
int x = 1, y = 2;
int sum = x + y;
// Point 对象消失了
```

**3. 锁消除。** 如果对象不逃逸出方法，不可能被其他线程访问，同步操作可以安全去除：

```java
// JIT 发现 sb 不会逃逸
public String concat(String[] parts) {
    StringBuilder sb = new StringBuilder();  // 局部变量，不逃逸
    for (String part : parts) {
        sb.append(part);  // synchronized 块被消除
    }
    return sb.toString();
}
```

## 5.5 去优化（Deoptimization）

JVM 有时会"倒退"回解释执行。原因：

编译时做了**激进假设**（如"这个接口只有一个实现"），运行时假设失效（新类被加载），JVM 主动回退到解释执行，用新的 profiling 数据重新编译。

```
C2 编译（假设只有 1 个实现）
      ↓ 新的实现类被加载
假设失效 → 去优化 → 回到解释执行
      ↓ 重新 profiling
C2 重新编译（考虑多个实现）
```

去优化是 JVM 自适应优化的一部分——它不是错误，而是 JVM 根据运行时信息动态调整策略的机制。
