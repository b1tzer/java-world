# 第七卷 性能与架构 —— 系统如何在高并发、大规模场景下持续演进

> 前六卷培养的是一个能写出高质量 Java 后端服务的工程师，第七卷培养的是一个能**设计复杂业务系统**的工程师。把前六卷能力整合为系统设计能力，回答：系统为什么这样拆？如何保证高可用与高并发？如何权衡一致性、性能和成本？共 9 章。

---

## 1 架构思想与分层设计

本章目标：建立架构思维，区分"代码设计"与"架构设计"。合并原"架构思想"和"分层架构"两章。

### 1.1 什么是软件架构

| 代码设计 | 架构设计 |
|---------|---------|
| `class` / `method` / `module` | `service` / `database` / `network` / `deployment` |
| 关注代码怎么组织 | 关注系统怎么拆分与协作 |

架构不是技术选型，而是在约束（用户规模、成本、团队、业务复杂度）下寻找合理的系统结构。

### 1.2 架构演进规律

```
单体 → 垂直拆分 → SOA → 微服务 → 云原生
```

演进驱动力：用户规模增长 → 流量压力 → 组织膨胀 → 需要更细粒度的分治。过度设计（微服务地狱）和不足设计（单体泥球）都是陷阱。

### 1.3 分层架构

经典三层：

```
Controller（接收请求、参数校验）
      ↓
Service（业务逻辑编排）
      ↓
Repository（数据访问）
```

每一层只依赖下一层，不反向依赖。

### 1.4 六边形架构（Ports & Adapters）

核心思想：**业务核心不依赖外部**。

```
外部世界（HTTP / MQ / DB）
      ↕ 通过 Adapter 连接
Port（抽象接口）
      ↕
Domain Core（纯业务逻辑）
```

更换数据库只需换 Adapter，业务核心不动。

### 1.5 Clean Architecture

依赖方向只从外向内：Frameworks → Interface Adapters → Application Rules → Enterprise Rules。外层变化不影响内层。

### 1.6 模块边界设计

高内聚（一起变的东西放在一起）、低耦合（模块间通过接口交互）、单一职责（一个模块只有一个要改的原因）。

## 2 领域驱动设计（DDD）

本章目标：理解传统 CRUD 在复杂系统中为什么失效，以及如何用领域模型驱动代码设计。精简战略设计细节，聚焦核心概念。

### 2.1 为什么传统 CRUD 会失效

当业务规则散落在 Service 层的 `if/else` 中，系统越来越难改。DDD 的价值：用模型承载规则。

### 2.2 核心概念

| 概念 | 含义 | 举例 |
|------|------|------|
| Entity | 有唯一标识，可变 | Order（订单 ID 不变，状态可流转） |
| Value Object | 无标识，不可变 | Money（金额 + 币种） |
| Aggregate | 一组相关对象的聚合根 | Order（聚合根）+ OrderItem（内部实体） |
| Bounded Context | 每个上下文有自己的模型语言 | "用户"在订单上下文和营销上下文中含义不同 |

### 2.3 领域建模过程

```
业务分析 → 识别 Entity / Value Object / Aggregate → 划分 Bounded Context → 代码落地
```

关键：模型必须反映业务语言，不是数据库表的镜像。

### 2.4 战术设计

- **Repository**：仓储接口，定义在领域层，不依赖具体 ORM
- **Domain Service**：无状态、跨实体的领域逻辑
- **Application Service**：编排用例流程

核心原则：**领域层不依赖任何框架**——没有 `@Autowired`，没有 `@Entity`。

## 3 高并发系统设计

本章目标：连接第三卷并发与第五卷数据访问——高并发的本质是资源竞争，以及从架构层面如何应对。

### 3.1 高并发问题本质

| 竞争资源 | 典型瓶颈 |
|---------|---------|
| CPU | 计算密集型任务耗尽核心 |
| 内存 | 大量并发对象 → GC 停顿 |
| I/O | 网络带宽、磁盘吞吐 |
| 数据库 | 连接数、锁竞争 |

### 3.2 流量模型

| 指标 | 含义 |
|------|------|
| QPS | 每秒请求数 |
| TPS | 每秒事务数 |
| RT | 响应时间，关注 P50 / P99 |

经验公式：`并发数 = QPS × 平均 RT`。

### 3.3 水平扩展与无状态设计

- 垂直扩展：加 CPU、加内存，有上限
- 水平扩展：加机器，前提是服务无状态

无状态 = 任意机器都能处理任意请求。实践：Session 外置到 Redis，Cookie 携带 Token。

### 3.4 高并发经典架构

```
用户请求 → CDN（静态资源）
              ↓
         API Gateway（鉴权、限流、路由）
              ↓
         Service（无状态，可水平扩展）
              ↓
         Cache（Redis，热点数据）
              ↓
         Database（主从 + 分库分表）
```

逐层消峰，逐层缓存，逐层降级。

## 4 高可用系统设计

本章目标：可用性是可量化的工程指标，保证高可用的核心手段：冗余、隔离、降级。

### 4.1 可用性量化

| 级别 | 年不可用时间 |
|------|------------|
| 99.9%（三个九） | 约 8.76 小时 |
| 99.99%（四个九） | 约 52 分钟 |
| 99.999%（五个九） | 约 5 分钟 |

### 4.2 消除单点故障

任何一台机器/服务/网络节点挂掉就影响全局，就是单点。高可用第一步：消除所有单点。

### 4.3 冗余设计

主备（Active-Standby）、集群（Active-Active）、多副本。

### 4.4 故障隔离

服务隔离（一个服务挂不影响其他）、线程池隔离（不同接口独立线程池）、舱壁模式（限制单个下游并发连接数）。

### 4.5 优雅降级

| 策略 | 行为 |
|------|------|
| Fallback | 调用失败返回默认值或缓存数据 |
| 熔断 | 错误率超阈值时快速失败 |
| 降级 | 高峰期关闭非核心功能，保证核心链路 |

## 5 分布式系统核心问题

本章目标：分布式系统的复杂性来自"网络不可靠"这一根本事实。

### 5.1 CAP 理论

| 字母 | 含义 |
|------|------|
| C（Consistency） | 所有节点同一时刻看到相同数据 |
| A（Availability） | 每个请求都能得到非错误响应 |
| P（Partition Tolerance） | 部分节点无法通信时仍能工作 |

P 是必须面对的。CAP 的本质：分区发生时，选 C 还是选 A。

### 5.2 一致性模型

强一致（写入后立刻对所有后续读可见）、弱一致（不保证立即可见）、最终一致（经过一段时间后最终一致）。

### 5.3 分布式事务

| 方案 | 原理 | 适用场景 |
|------|------|---------|
| 2PC | 协调者先问再统一提交 | 强一致，但性能差 |
| TCC | 预留资源 → 确认 → 取消 | 资金交易类 |
| Saga | 长事务拆分为多个本地事务 + 补偿 | 微服务间数据一致性 |

### 5.4 分布式锁

| 方案 | 特点 |
|------|------|
| Redis（SET NX + 过期时间） | 高性能，有锁过期风险，Redisson 提供看门狗 |
| ZooKeeper（临时顺序节点） | 可靠性高，性能低于 Redis |
| 数据库（唯一索引） | 最简单，性能最差 |

## 6 数据架构：缓存与大规模数据

本章目标：合并原 Redis 缓存体系和分库分表设计。这是从第五卷"持久化"延伸出来的数据层架构能力。

### 6.1 Java 缓存体系

| 客户端 | 特点 |
|--------|------|
| Jedis | 同步、简单，早期主流 |
| Lettuce | 异步、线程安全，Spring Boot 2.x 默认 |
| Redisson | 分布式对象、锁、集合，高级抽象 |

Spring Cache 抽象：`@Cacheable` / `@CacheEvict` / `@CachePut` 提供声明式缓存管理，底层可切换 Caffeine（本地）或 Redis（分布式）。

### 6.2 缓存一致性策略

| 策略 | 写操作 | 风险 |
|------|--------|------|
| Cache Aside | 更新 DB → 删除缓存 | 短暂不一致 |
| Read/Write Through | 缓存层代理 DB 读写 | 缓存与 DB 强耦合 |
| 延迟双删 | 删缓存 → 更新 DB → 延迟再删 | 降低但不根除不一致概率 |

### 6.3 三大经典问题

| 问题 | 现象 | 解决 |
|------|------|------|
| 穿透 | 查不到的数据反复穿透到 DB | 布隆过滤器 / 缓存空值 |
| 击穿 | 热点 key 过期瞬间大量请求打 DB | 互斥锁 / 逻辑过期 |
| 雪崩 | 大量 key 同时过期 | 过期时间加随机值 / 多级缓存 |

### 6.4 分库分表设计

数据增长路径：百万 → 千万 → 上亿，不拆分无法继续。

三个核心问题：

| 问题 | 决策 |
|------|------|
| 分片键选什么？ | 最常用的查询条件（通常 user_id 或 order_id） |
| 如何路由？ | 中间件（ShardingSphere）或客户端路由 |
| 如何扩容？ | 停机扩容 vs 平滑扩容（一致性哈希 + 数据迁移） |

分片键选错是灾难——跨片查询、跨片排序、跨片事务都会大幅增加复杂度。

### 6.5 数据冷热分离

| 数据类型 | 占比 | 存储 |
|---------|------|------|
| 热数据 | ~10% | 高性能存储（内存/SSD） |
| 温数据 | ~30% | 普通数据库 |
| 冷数据 | ~60% | 低成本存储（归档） |

### 6.6 多数据源一致性

当数据在多个地方（MySQL + Redis + ES），如何保持一致：

| 策略 | 方式 | 风险 |
|------|------|------|
| 双写 | 同时写 MySQL 和 Redis | 部分失败导致不一致 |
| 异步同步 | Canal 监听 binlog → 同步到 ES/Redis | 有延迟 |
| 最终一致 + 对账 | 异步同步 + 定时任务校验修复 | 需接受短时间不一致 |

## 7 消息驱动架构

本章目标：异步不是"让请求变快"的银弹，而是解耦生产者和消费者的架构手段。

### 7.1 同步链路的局限

```
Request → Service A → Service B → Service C → Response
```

链路过长，任意环节阻塞拖慢整体。异步化：

```
Request → Service A → MQ → Service B（异步消费）→ Service C（异步消费）
```

### 7.2 事件驱动设计

核心是 Event：**"什么事发生了"**。生产者发布事件，消费者订阅事件，双方通过 MQ 解耦，互不知道对方存在。

### 7.3 Kafka 的角色

| 场景 | 用法 |
|------|------|
| 日志采集 | 各服务日志 → Kafka → ELK |
| 数据同步 | binlog → Kafka → 下游 |
| 异步解耦 | 下单事件 → Kafka → 库存/通知/积分 |
| 流计算 | Kafka → Flink → 实时报表 |

### 7.4 消息可靠性

| 机制 | 作用 |
|------|------|
| 消息持久化 | 落盘，重启不丢 |
| 消费者 ACK | 处理完再确认 |
| 幂等消费 | 数据库唯一约束 + 业务幂等 |
| 死信队列 | 多次重试失败的消息，人工介入 |

## 8 性能工程

本章目标：性能优化不是凭感觉调参数，而是科学的闭环流程。连接第二卷 JVM 知识。

### 8.1 性能指标体系

| 指标 | 含义 |
|------|------|
| Latency | 单个请求处理时间（P50 / P95 / P99） |
| Throughput | 单位时间处理的请求量 |
| Error Rate | 错误请求占比 |
| Saturation | 资源饱和度（CPU / 内存 / I/O） |

### 8.2 性能分析方法

| 方法 | 工具 | 场景 |
|------|------|------|
| Profiling | Arthas、JProfiler、async-profiler | CPU 热点、内存分配 |
| Benchmark | JMH | 微基准测试 |
| 压测 | JMeter、wrk | 系统在给定负载下的表现 |

### 8.3 JVM 性能诊断实战

| 场景 | JVM 工具 |
|------|---------|
| CPU 100% | Arthas `thread -n 3` + `jstack` |
| 内存泄漏 | `jmap -histo` + MAT 分析 heap dump |
| 频繁 GC | `jstat -gcutil` 观察 GC 次数和耗时 |
| 接口变慢 | Tracing 定位慢调用链 |

### 8.4 优化方法论

```
发现问题（监控 / 压测）
  → 定位瓶颈（Profiling / Tracing / 日志）
  → 提出假设 → 改动 → 验证
  → 持续监控，防止回退
```

核心原则：**没有测量就没有优化**。先确认瓶颈在哪，再对症下药。

## 9 架构案例分析

本章目标：综合全书能力，通过三个接近真实业务的案例，学习如何在具体约束下做架构决策。

### 9.1 案例一：高并发秒杀系统

涉及：第三卷（并发安全）、第五卷（数据库事务）、第七卷（缓存/限流/MQ）。

| 问题 | 方案 |
|------|------|
| 瞬时高流量 | 网关限流 + CDN 静态化 + 验证码削峰 |
| 库存扣减超卖 | Redis 预减库存 + Lua 原子操作 |
| 订单异步处理 | 扣减成功 → 发 MQ → 订单服务异步生成 |
| 保证下单成功 | 分布式事务（本地事务表 + 消息重试） |

### 9.2 案例二：社交 Feed 流系统

涉及：第四卷（网络通信）、第五卷（数据库）、第七卷（缓存/分库分表）。

| 问题 | 方案 |
|------|------|
| Feed 推还是拉 | 大 V 用"拉"，普通用户用"推" |
| 热点缓存 | 热门 Feed 缓存到 Redis |
| 时间线一致性 | 版本号 + 增量同步 |
| 海量数据存储 | 按 user_id 分片 + 冷热分离 |

### 9.3 案例三：支付系统

涉及：第五卷（事务）、第六卷（安全）、第七卷（分布式事务/一致性）。

| 问题 | 方案 |
|------|------|
| 资金一致性 | TCC 两阶段（Try 冻结 → Confirm 扣款 → Cancel 解冻） |
| 幂等扣款 | 全局唯一交易号 + 数据库唯一约束 |
| 对账 | 定时比对内部流水与第三方账单 |
| 安全 | 鉴权 + 签名验证 + 敏感信息加密 + 操作审计 |
